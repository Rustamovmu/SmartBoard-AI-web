## 2026-11-02 — Authentication increment

Source: existing `smartbord-ai-frontend-web` Pages Router starter on `develop`; Next.js 16.4.4 and React 19.3.0 retained. Backend/mobile repositories stay separate. Yarn 1.22.22 replaces npm here only. Yarn's importer rejected the starter's package-lock v3, so a fresh Yarn resolution was generated with the pinned framework versions and committed as `yarn.lock`.

Implemented: product home/layout, signup/login forms, protected current-account SSR, request-scoped/no-store identity fetch, credentialed browser auth, CSRF, Web Locks across tabs, strict rotating refresh, ambiguous-refresh failure marker, logout, session notifications/revalidation and real pending/denied/outage states. Auth uses the existing backend endpoints without adding a production route or changing cookie/DB policies. SSR never rotates credentials. Adapted route/component/auth boundaries, not roles, ports, business data or token globals. Official Next Pages/SSR, Yarn migration, Playwright browser and Chromium verifier documentation informed the implementation. Chromium ignores macOS hostname-policy trust settings; the harness instead uses SSL trust with critical X.509 name constraints on its ephemeral root. Sources: [Yarn migration](https://classic.yarnpkg.com/lang/en/docs/migrating-from-npm/), [Next SSR](https://nextjs.org/docs/pages/building-your-application/data-fetching/get-server-side-props), [Playwright browser modes](https://playwright.dev/docs/browsers), [Chromium verifier](https://chromium.googlesource.com/chromium/src/+/main/net/cert/internal/trust_store_mac.cc).

## 2026-11-02 — Fix ordinary development signup and React title

The user's screenshots established two issues in the ordinary development path: `yarn dev` ran `next dev` over HTTP, so the auth client's exact-HTTPS check correctly refused signup; the shared `<title>` also had multiple children and emitted a React warning. The earlier production HTTPS fixture was valid evidence for that isolated path, but did not establish a usable everyday development setup.

Changed the default Yarn dev command to a loopback HTTPS launcher with a second HTTPS API listener forwarding by streams to a fixed `http://127.0.0.1:4001` backend. The backend remains a separately launched app with its existing default port/configuration; README supplies the explicit 4001 invocation and exact browser origin. The launcher checks certificates/ports, supplies its web child with CA trust before Node startup, shuts down its own listeners and never stops a pre-existing process. It does not copy credentials into JSON, change cookies/CSRF or create application accounts. Proxy bodies are neither logged nor written/buffered to disk. A one-time, opt-in `setup:https` generates ignored localhost-constrained SSL certificates with restricted permissions and user keychain trust. Those development files/trust are intentionally persistent and removable by the documented exact-checkout command; test-owned resources remain disposable.

The auth form now disables credential entry on the wrong/HTTP origin and links to the configured HTTPS signup/login page before submission. The title uses a single template string, following [React's title contract](https://react.dev/reference/react-dom/components/title). `yarn run check` uses a source-only tsconfig while Next build keeps its own generated-route validation. This avoids actual missing/duplicate cache-validator errors observed while the user's Next dev server was running. No dependency/framework/router/module configuration was migrated.
